# Reference relay

The first relay is deterministic and in-memory. It accepts versioned client
command envelopes, owns per-session ordering and message deduplication, and
produces canonical room snapshots. It exists for protocol tests, local client
development, and reproducible demonstrations. It is not the production
Supabase deployment and does not imply a supported self-hosting product.

The core relay implements semantic ordering and state transitions. Phase 3 also
includes a deliberately small WebSocket development transport so two native
clients can exercise the protocol over a local network. It is not the
production Supabase deployment and does not provide durable rooms, public
authentication, or internet-facing abuse protection.

## Run the Phase 3 development relay

From the repository root:

```sh
npm install
npm run dev:relay
```

The command prints a `ws://` URL for each LAN address on the host. Enter the
same reachable URL on both test devices. Rooms contain at most two participants,
expire after six hours, and disappear whenever the process restarts.
Use this plain `ws://` endpoint only on a trusted development network.

The development transport accepts `room.create`, `room.join`,
`session.reconnect`, `room.command`, and `clock.ping` JSON frames. It also
accepts `session.drop` from an active development client. That frame closes the
requesting socket so native reconnect behavior can be tested without changing
Wi-Fi or waiting for the operating system to suspend an app. Session credentials
are generated by the relay. Playback commands and snapshots remain the
versioned, content-blind protocol envelopes published under `spec/`.

`room.create` may include `initialPositionMs`. The relay starts the room paused
at that position, so creating a room keeps the host's current playback point.
Older development clients that omit the field still start at zero.
